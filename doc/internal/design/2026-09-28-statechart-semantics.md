# Statechart-слой: семантика иерархии, регионов, history, таймеров и адаптера

- 更新日: 2026-09-28

Документ фиксирует семантику фаз 4–7 из
[roadmap](2026-09-28-statechart-roadmap.md) до кода. Всё живёт в модуле
`koma-statechart` и использует только публичный API `koma-core` (план B). Все
новые публичные типы помечены `@ExperimentalKomaApi`.

## Модель

Модель остаётся плоским списком узлов. Дерево задаётся ссылкой на родителя.
Так существующие определения (`AtomicState(id)`) продолжают работать без
изменений, а валидатор и экспорт обходят один список.

| Узел | Поля | Смысл |
|---|---|---|
| `AtomicState` | `id`, `parent: StateId? = null` | Лист |
| `CompoundState` | `id`, `initial: StateId`, `parent` | Ровно один активный ребёнок |
| `ParallelState` | `id`, `parent` | Активны все дети (регионы) одновременно |
| `HistoryState` | `id`, `parent`, `deep: Boolean`, `default: StateId?` | Псевдо-узел: переход в него восстанавливает прошлую конфигурацию родителя |

`StateChartDefinition.initial` указывает на корневой узел. Корней может быть
несколько: тогда корень чарта ведёт себя как неявный compound.

Триггер перехода — sealed `Trigger`:

- `Trigger.OnAction(matcher)` — приход action, как сейчас;
- `Trigger.After(delay: Duration)` — таймер, который запускается при входе в
  `source` и отменяется при выходе из него.

`Transition(source, target, on: ActionMatcher, guard)` остаётся вторичным
конструктором, поэтому существующий код не меняется. Свойство `on` возвращает
matcher для `OnAction` и `null` для таймера.

У перехода появляется необязательная метка `effect: String?`. Как и у guard, это
только метка. Реализацию даёт адаптер к Store.

## Конфигурация

`StateConfiguration` — неизменяемое значение:

- `active: Set<StateId>` — активные узлы, включая всех предков;
- `history: Map<StateId, Set<StateId>>` — запомненные дети/листья для узлов,
  у которых есть `HistoryState`.

Runtime остаётся чистой функцией. Конфигурацию хранит вызывающий: Koma Store в
поле состояния.

## Шаг (step)

Семантика упрощённого SCXML (microstep без eventless-переходов):

1. **Выбор переходов.** Активные листья обходятся в порядке объявления узлов.
   Для каждого листа ищется первый переход в порядке объявления: сначала у
   самого листа, потом у предков, изнутри наружу. Переход подходит, если
   сработал триггер и guard отсутствует или вернул `true`. Так внутренний
   переход имеет приоритет над внешним, как в Harel/SCXML.
2. **Конфликты.** Два выбранных перехода конфликтуют, если их exit-множества
   пересекаются. Тогда побеждает выбранный раньше. Поэтому переходы в разных
   регионах срабатывают вместе, а переход родителя над регионами выполняется
   один раз.
3. **Exit-множество** перехода — активные потомки LCCA(source, target).
   LCCA — ближайший общий compound-предок; для self-loop это родитель source,
   то есть переход внешний: source выходит и входит заново. Exit идёт
   изнутри наружу, потом по обратному порядку объявления. Перед выходом из
   узла с `HistoryState` запоминается shallow (активный ребёнок) или deep
   (активные листья).
4. **Enter-множество**: цепочка от LCCA до target, дальше рекурсивно.
   Compound входит в `initial`. Parallel входит во все регионы. `HistoryState`
   восстанавливает запомненное, а если ничего нет — `default` или `initial`
   родителя. Enter идёт снаружи внутрь, в порядке объявления.
5. **Результат**: `StepResult.Transitioned(transitions, exited, entered,
   configuration)` или `StepResult.Ignored`. Для таймеров результат содержит
   `timersToStart` (переходы `After` из вошедших узлов) и `timersToCancel`
   (из вышедших узлов).

`StateChartRuntime.initialConfiguration()` выполняет вход в `initial`.
`step(configuration, state, action)` обрабатывает action.
`fire(configuration, state, timer)` обрабатывает таймер: если его source ещё
активен, срабатывает этот переход, если guard пропускает.

## Валидация

К текущим проверкам добавляются:

- неизвестный родитель; цикл в цепочке родителей;
- `CompoundState.initial` не является его ребёнком;
- у `ParallelState` меньше двух регионов;
- `HistoryState` с детьми или вне compound/parallel; `default` вне родителя
  (точные правила — в «Решения волны 2»);
- переход, чей source — `HistoryState`;
- `Trigger.After` с неположительной задержкой.

## Mermaid

Вложенные `state X { ... }`, регионы через `--`. History выводится как
`[H]` / `[H*]` в виде подписанного узла. Таймер выводится как `after 5s`.

## Пути и conformance

- `shortestPathTo` и `transitionCoveragePaths` работают на графе
  конфигураций (BFS из начальной конфигурации через `step`). Guard'ы при этом
  считаются истинными, а таймеры — шагами.
- `StateChartConformance` принимает `stateIdOf`, возвращающий активный лист, и
  ищет переход у листа и его предков. Переход в compound считается верным,
  если новый лист входит в enter-множество.

## Адаптер к Store (фаза 4)

Без изменений ядра, через один catch-all обработчик:

```kotlin
data class ChartState<C>(val configuration: StateConfiguration, val context: C) : State

val store = StateChartStore<C, A, E>(
    definition = chart,
    context = initialContext,
    guards = mapOf("canRetry" to { s, _ -> s.context.attempts < 3 }),
    effects = mapOf("countAttempt" to { ctx, _ -> ctx.copy(attempts = ctx.attempts + 1) }),
    onEnter = mapOf(loading to { /* launch работу, emit event */ }),
)
```

- Класс Koma-state не меняется (`ChartState`), поэтому Koma не делает
  exit/enter. Время жизни работы под узлом держит адаптер: `launch` в
  `onEnter` получает `LaunchLane` узла, и при выходе из узла адаптер
  вызывает `cancelLaunch(lane)`.
- Таймеры запускаются как `launch { delay(d); transaction { … fire … } }` с
  lane перехода и отменяются так же.
- Порядок в одном шаге: exit-обработчики (изнутри наружу), затем effects
  переходов (в порядке выбора), затем enter-обработчики (снаружи внутрь). Всё
  выполняется одной транзакцией Koma, поэтому UI видит одно новое состояние.
- Store остаётся обычным `Store<ChartState<C>, A, E>`: `koma-test`,
  `Plugin`, `StateSaver` и Compose работают без изменений.

## Решения волны 1 (иерархия)

Уточнения, которых не было выше; код в ветке `feature/statechart-hierarchy`.

- **LCCA** — ближайший compound-предок, который является *собственным*
  предком и source, и target (для верхнего уровня — неявный корень). Поэтому
  все переходы внешние: не только self-loop, но и переход из узла в его
  потомка (`Online → Typing`: exit Idle, Online; enter Online, Chat, Typing) и
  из узла в его предка (`Reading → Online`: exit Reading, Chat, Online; enter
  Online, Idle). Внутренних (`type="internal"`) переходов нет.
- **`initial` может быть вложенным узлом.** Тогда входят его предки снаружи
  внутрь, сам узел и цепочка `initial` вниз. Валидатор это не запрещает.
- **Неизвестные id** (необъявленный `initial` или target) ведут себя как
  атомарные узлы верхнего уровня. Так пути и reachability на невалидных
  чартах работают как раньше.
- **Runtime отвергает сломанную иерархию**: конструктор бросает
  `IllegalArgumentException` при `UnknownParent`, `AtomicParent`,
  `ParentCycle`, `InitialNotChild`, `EmptyCompoundState`. Validate, Mermaid,
  пути и conformance на таких чартах не падают и не зацикливаются: подъём по
  родителям останавливается на повторе и на необъявленном родителе.
- **Проверки валидатора** идут после дубликатов и `initial`, перед концами
  переходов: сначала неизвестный или атомарный родитель по узлам в порядке
  объявления, затем циклы (каждый один раз, начиная с первого объявленного
  узла, в порядке их первых узлов), затем `initial` не ребёнок, затем пустой
  compound. При дублях id берётся первое объявление.
- **Reachability и пути** обходят конфигурации BFS, как и было в разделе про
  пути, но в каждой конфигурации годится *любой* переход с активным source:
  guard'ы и приоритет (внутренний переход закрывает внешний) не учитываются.
  Узел достижим, если он активен хоть в одной достижимой конфигурации;
  `shortestPathTo(x)` ведёт в первую найденную такую конфигурацию.
- **`StateChartPath`** получил третье поле `leaves` — активный лист после
  каждого перехода; `start` — лист начальной конфигурации, `end` — последний
  лист. Старый конструктор `(start, transitions)` остался: он проверяет
  связность плоского пути и берёт `leaves` из target'ов.
- **`StepResult.Transitioned`** теперь `(transitions, exited, entered,
  configuration)`. Вторичный конструктор `Transitioned(transition)` строит
  результат плоского шага (`exited = [source]`, `entered = [target]`,
  `active = {target}`) и равен тому, что runtime возвращает для плоского
  чарта. `transition` — первый выбранный переход, `target` — его target (для
  compound-target новый лист — `entered.last()`).
- **`step(state, action)`** остался и строит конфигурацию из
  `stateIdOf(state)` через `configurationOf(leaf)` (лист и его предки).
  Порядок `active` — снаружи внутрь.
- **Conformance**: кандидаты перехода из листа `from` — переходы листа и его
  предков в порядке приоритета; переход ведёт в `to`, если `to` входит в его
  enter-множество из `configurationOf(from)`. Self-loop — переход, после
  которого лист тот же (например, self-loop compound-предка, чей `initial` —
  текущий лист).
- **Mermaid**: в блоке compound сначала `[*] --> initial`, потом все дети
  (атомарные — отдельной строкой, чтобы попасть внутрь блока), потом переходы,
  у которых этот блок — ближайший общий собственный предок концов. Узлы со
  сломанным родителем рисуются на верхнем уровне.
- **Несколько активных листьев** (появятся с регионами) уже выбираются по
  правилу раздела «Шаг»: переход листа отбрасывается, если его exit-множество
  пересекается с уже выбранным. Переход с доменом-корнем выходит из всего.
- **`Trigger`** пока не введён: `Transition.on: ActionMatcher` без изменений,
  sealed `Trigger` появится в волне таймеров. `StateConfiguration.history`
  есть и всегда пуст до волны history.

## Решения волны 2 (history)

Уточнения; код в ветке `feature/statechart-history`.

- **Модель.** `HistoryState(id, parent: StateId, deep = false, default: StateId? = null)`.
  `parent` не nullable: history верхнего уровня не бывает. Сейчас родитель —
  только `CompoundState`; для `ParallelState` запись и восстановление уже
  написаны для множеств (несколько детей, несколько листьев).
- **Ключ `StateConfiguration.history` — id самого `HistoryState`**, а не
  родителя. Так у одного родителя могут быть и shallow, и deep history: каждая
  помнит своё (shallow — активного ребёнка, deep — активные атомарные листья).
  Пустая запись не хранится: нет ключа — значит, ничего не запомнено.
- **Когда пишется.** В microstep сначала считается exit-множество, потом для
  каждого выходящего узла пишутся все его history (по конфигурации *до*
  шага), и только потом считается вход. Поэтому переход, который выходит из
  родителя и целится в его history (например, `Chat → ChatHistory`),
  восстанавливает только что записанное. Переход внутри родителя
  (`Sending → ChatHistory`, LCCA = `Chat`) из родителя не выходит и
  восстанавливает прежнюю запись.
- **Вход.** Цель-history сама не входит никогда: входят предки history ниже
  LCCA, затем для каждого запомненного узла цепочка от родителя до него и его
  `initial` вниз. Нет записи — `default`, нет `default` — `initial` родителя.
  `StepResult.entered` содержит только настоящие узлы; `target` остаётся
  history (новый лист — `entered.last()`).
- **Валидация** (новые `ValidationIssue`):
  `HistoryParent` (у history есть дети; проверяется вместе с
  unknown/atomic parent), затем группа history после иерархии:
  `HistoryAsInitial(null, h)` — history как `initial` чарта,
  `HistoryAsInitial(compound, h)` — как `initial` своего родителя (history
  чужого родителя остаётся `InitialNotChild`), `InvalidHistoryDefault` —
  shallow: `default` должен быть ребёнком родителя, deep: любым собственным
  потомком; в обоих случаях объявленным и не history (проверяется, только
  если родитель — объявленный compound). `TransitionFromHistory` —
  в блоке концов переходов, после unknown source/target того же перехода.
  History с неизвестным или атомарным родителем — это уже `UnknownParent` /
  `AtomicParent`. Несколько history у одного родителя разрешены.
  `UnreachableState` для history не выдаётся никогда: она не бывает активной.
- **Runtime отвергает** всё, что делает вход неопределённым: иерархические
  проблемы (включая `HistoryParent`) плюс `HistoryAsInitial` и
  `InvalidHistoryDefault`. `TransitionFromHistory` только предупреждение:
  такой переход просто никогда не срабатывает.
- **Невалидные чарты в инструментах.** History, которую нельзя разрешить
  (родитель не compound, `default`/`initial` не потомок), входит как атомарный
  узел, как и необъявленные id. Пути, reachability и Mermaid не падают и не
  зацикливаются.
- **`step(state, action)` без конфигурации** строит `configurationOf(leaf)` —
  с пустой history, поэтому для чартов с history нужен вариант с
  конфигурацией (её хранит вызывающий).
- **Пути и reachability** идут по полным конфигурациям (`active` + `history`):
  так кратчайший путь проигрывается runtime'ом один в один. Граф конечен:
  каждая запись — подмножество объявленных узлов. Граф по-прежнему строится
  один раз на определение (`configurationGraph` в `Model.kt`).
- **Conformance** сам ведёт history по смене листьев по тем же правилам
  (после необъяснённой смены выходящими считаются предки старого листа, не
  являющиеся предками нового; self-loop ничего не пишет). Переход в history
  ведёт в `to` строго по отслеживаемой записи, поэтому Store, который «забыл»
  восстановить экран, получает `UndeclaredTransition`. Если плагин ещё не
  видел записи этой history (например, Store стартовал из сохранённого
  состояния), принимается любой лист, который history могла бы восстановить:
  `default`/`initial` и восстановление каждого ребёнка (shallow) или
  атомарного потомка (deep) родителя.
- **Mermaid.** History — узел с меткой `[H]` / `[H*]`, всегда объявленный
  через `state "[H]" as ref` в блоке родителя (ref — id или безопасный alias).
  `default` рисуется немаркированным ребром `ref --> default` в том же блоке,
  где лёг бы такой переход, перед переходами блока.

## Порядок волн

1. Иерархия: модель, валидация, Mermaid, runtime с конфигурацией, пути,
   conformance.
2. History.
3. Параллельные регионы.
4. Таймеры (`Trigger.After`).
5. Адаптер `StateChartStore` с effects, onEnter/onExit и таймерами.
6. Пример «мессенджер» в тестах и обновление roadmap.

Каждая волна — отдельная ветка и PR в форке, со своими property-тестами.
