# Summary of changes from 3.1.0 → 4.0.0-beta01

- Updated: 2026-05-09

## Background

Between 3.1.0 and 4.0.0-beta01, the user-facing API changed across a wide range: the replacement of Middleware → Plugin, turning Store lifecycle control into policies, the addition of `koma-test`, the rework of the Compose integration, and so on.
This is compiled as a cross-cutting summary, as a reference for users migrating from 3.1.0 and as an inventory of the features that became newly available in 4.0.

The reasons for each individual decision are kept separately under `adr/`, so here we only list what changed and where to touch when migrating.

## A. Breaking changes (places where 3.1.0 code no longer works as-is)

### A-1. Complete removal of Middleware → replacement with Plugin

- `Middleware<S, A, E>` / `MiddlewareScope<A>` removed. Replaced with `Plugin<S, A, E>` / `PluginScope<S, A>`.
  - Related: `koma-core/src/commonMain/kotlin/koma/core/Plugin.kt`, `PluginScope.kt`
- Hook granularity greatly reduced. The old 12 hooks (`before/afterActionDispatch`, `before/afterEventEmit`, `before/afterStateEnter`, `before/afterStateExit`, `before/afterStateChange`, `before/afterError`) are all removed.
  - The new API has only the 4 hooks `onStart` / `onAction` / `onState` / `onEvent`.
  - Processing such as re-dispatching in the `afterError` family needs to be moved to the `ExceptionHandler` or the `error {}` handler side.
- `StoreBuilder.middleware(...)` / `middlewares(...)` removed. Replaced with `plugin(first, vararg rest)`.
- `koma-logging`: `LoggingMiddleware` abstract class removed. `simpleLogging(...)` remains, but its return type is `Plugin`.
- `koma-message`: `MessageMiddleware.kt` removed. `receiveMessages(...)` remains, but its return type is `Plugin`, and the lambda receiver changes from `MiddlewareScope<A>` → `PluginLaunchScope<S, A>`.

### A-2. `Store` interface

- `dispose()` is `@Deprecated`. Unified into `close()`. `Store` extends `AutoCloseable`.
- The 2 flag arguments of `collectState(skipInitialState, startStore, state)` removed. Only `collectState(state)`.
- Auto-start behavior consolidated into `AutoStartPolicy`; with the default `OnDispatchOrStateCollection`, collecting `event` does not start the Store / reading `currentState` does not start the Store.
  - Code that in 3.1.0 expected initialization to run from event subscription or `currentState` reference alone needs review.

### A-3. `Store(...)` factory

- The 2 overloads (`Store(initialState, block)` / `Store(block)`) consolidated into 1.
  - New signature: `Store(initialState: S? = null, context: CoroutineContext? = null, builder: StoreBuilder<...>.() -> Unit)`
  - Lambda argument name `block` → `builder`. Named calls with `block = ...` break.

### A-4. DSL argument names, defaults and type changes

- In the `enter` / `action` / `exit` / `error` DSL and `EnterScope.LaunchScope.transaction` etc., `coroutineDispatcher` → renamed to `dispatcher`.
- Type changed from `CoroutineDispatcher` → `CoroutineDispatcher?`, default from `Dispatchers.Unconfined` → `null` (= inherits the Store's context = default `Dispatchers.Default`).
  - Code that assumed `Unconfined` changes behavior.
- The upper bound of `error<T>` / `ErrorScope` changed from `Throwable` → `Exception`. `error<Throwable>` and `error<OutOfMemoryError>` are no longer possible.
- `ExceptionHandler.Default` removed and renamed to `ExceptionHandler.Unhandled` (same behavior: rethrow).
- `EnterScope<S, A, E, S2>` → `EnterScope<S, E, S2>`. Type parameter `A` removed.

### A-5. koma-compose

- `rememberViewStore(store, autoDispose)` → `rememberViewStore(key, autoClose, store)`.
  - The `store` argument became a `@Composable () -> Store<...>` lambda.
  - `autoDispose` → renamed to `autoClose`.
- `ViewStore.eventFlow` is `@PublishedApi internal`. Not referenceable from outside.
- The `block` of `ViewStore.render { ... }` must be a `@Composable` lambda.

### A-6. koma-logging

- `Logger` turned into a `fun interface`.
- `suspend` removed from `log(...)`.
- `message: String` → `message: () -> String` (lazy evaluation). Custom `Logger` implementations all need rewriting.
- `coroutineDispatcher` of `simpleLogging(...)` → `dispatcher: CoroutineDispatcher?`, return type `Plugin`.

### A-7. Other

- New opt-in annotation `@InternalKomaApi` added. Some APIs that were referenceable in 3.1.0 may have been made `internal` / made to require opt-in.

## B. New features added in 4.0

### B-1. New module `koma-test`

The public API is 2 files: `koma-test/src/commonMain/kotlin/koma/test/StoreExtensions.kt`, `StoreRecorder.kt`.

- `suspend fun Store<...>.startAndWait()`
  - Of `start()`, waits until the plugins' `onStart` and the `enter {}` chain at startup have finished.
- `suspend fun Store<...>.dispatchAndWait(action)`
  - Waits for the completion of the handler derived from that action and the synchronous transitions. Does not wait for work `launch`ed from `enter {}` / `action {}`.
- `Store<...>.patch { ... }`
  - DSL that replaces `stateSaver` / `coroutineContext` / `exceptionHandler` / each `*Policy` / `plugin(...)` etc. on a Store before it starts. Settings can be overridden in tests without changing production code.
- `Store<...>.createRecorder(): StoreRecorder<S, A, E>`
  - Installs a history-recording Plugin into the Store; the timeline can be obtained via `recorder.states` / `recorder.events`. Can be `clear()`ed.

### B-2. Plugin system

Core: `koma-core/src/commonMain/kotlin/koma/core/Plugin.kt`, `PluginScope.kt`.

- Can be created via the 4-hook `Plugin<S, A, E>` interface, or the `Plugin(onStart=…, onAction=…, onState=…, onEvent=…)` factory.
- `PluginScope<S, A>` allows `dispatch(action)` from the hook body, and `launch(dispatcher) { ... }` submits background work with the Store's lifetime. It survives across states and ends on `Store.close()`.
- Inside `PluginLaunchScope<S, A>`, `currentState` can also be read.
- `PluginExecutionPolicy`: `Concurrent` (default; runs in parallel and awaits all completions) / `InRegistrationOrder` (sequentially in registration order).

### B-3. The 3 lifecycle control policies

- `AutoStartPolicy`: `OnDispatchOrStateCollection` (default) / `OnDispatch` (does not start on state subscription).
- `PendingActionPolicy`: `ClearOnStateExit` (default; discards queued unexecuted actions on a state variant transition) / `Keep` (kept until an explicit `clearPendingActions()` call).
- Both configured via `StoreBuilder.autoStartPolicy(...)` / `pendingActionPolicy(...)`.

### B-4. launch / launch control in `ActionScope`

The `launch` that in 3.1.0 only `EnterScope` had is now also available in `ActionScope`.

- Inside `action {}`, `launch(dispatcher, control) { ... }` (→ `ActionLaunchScope` → `ActionTransactionScope`). A coroutine with the state's lifetime.
- `LaunchControl`:
  - `Concurrent` (default; no lane management)
  - `CancelPrevious(lane)` (cancels the previous one on the same lane and starts)
  - `DropIfRunning(lane)` (drops the new one while the previous one on the same lane is running)
- `LaunchLane`: key for explicit lanes. When omitted, an implicit lane per action type.
- `ActionScope.cancelLaunch(LaunchLane)`: cancels the tracked launch on an explicit lane.
- The `dispatcher` parameter of `launch` / `transaction` inside `enter {}` now defaults to `null` (inherits the Store's context), which is also new behavior.

### B-5. New API common to all regular scopes

In `EnterScope` / `ActionScope` / `ExitScope` / `ErrorScope`, and each `TransactionScope`:

- `clearPendingActions()`: discards only the unexecuted actions in the queue (does not stop running handlers/transactions). Can also be used for explicit clearing under the `PendingActionPolicy.Keep` setting.

### B-6. Direct `Store` operation API

- `fun start()`: explicitly requests start (returns immediately, does not wait for completion. To wait for completion, use `startAndWait()` from `koma-test`).
- `fun close()` + `AutoCloseable` implementation: the Store can be closed with `use { ... }`.

### B-7. Additional factory / builder DSL

- The `context` argument added to `Store(initialState = …, context = …) { … }` avoids writing `coroutineContext(...)` every time.
- `plugin(first, vararg rest)`, `autoStartPolicy(...)`, `pendingActionPolicy(...)` and `pluginExecutionPolicy(...)` added to `StoreBuilder`.

### B-8. Patch API (exposed via `koma-test`)

- `StorePatch` / `StorePatchBuilder`: overrides non-state Store settings before start. The plugin configuration can also be replaced with `plugin(append)` / `replacePlugins(...)` / `clearPlugins()`.
- Direct use is via `Store.patch { ... }` (`koma-test`).

### B-9. koma-compose reinforcement

- With `rememberViewStore(key, autoClose, store)` taking a lambda, the creation of the Store itself can be Composable (obtaining via DI, re-creation via `key`, etc.).
- The `LaunchedEffect` key of `ViewStore.handle { }` is now based on `eventFlow`, so it re-subscribes when the Store is swapped.
- `ViewStore.render { }` can now take a `@Composable` lambda, so nested Composables can be written directly.

### B-10. Improved expressiveness of koma-logging

- With the lazy evaluation of `Logger.log(... message: () -> String)`, no formatting cost is paid when disabled.
- `simpleLogging(...)` can be passed directly to `StoreBuilder.plugin(...)` as a `Plugin`.

## C. Migration impact

| Impact | Main targets |
|---|---|
| Must touch | Middleware → Plugin (including `koma-logging` / `koma-message`) / `Store(block)` overload / `ExceptionHandler.Default` / `rememberViewStore(store, autoDispose=…)` |
| Touch depending on usage | `collectState` flags / `error<Throwable>` / `EnterScope` type annotations / custom `Logger` implementations / named `coroutineDispatcher = ...` / `Store.dispose()` |
| API compiles but behavior changes | `event` collect / `currentState` read alone does not start the Store / default dispatcher of `enter` / `action` handlers changes from `Unconfined` → inherits the Store's context |
| New features available in 4.0 | `koma-test` (recorder / patch / *AndWait) / `Plugin` 4 hooks + `PluginScope.launch` / `AutoStartPolicy` / `PendingActionPolicy` / `PluginExecutionPolicy` / `ActionScope.launch` + `LaunchControl` / `LaunchLane` / `cancelLaunch` / `clearPendingActions()` in all scopes / `Store.start()` / `close()` / `AutoCloseable` / `Store(initialState, context) { }` |
